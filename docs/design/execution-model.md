## 执行与宿主约束

本节的统一线程契约与共享协调属于阶段三；阶段一迁移上游原生线程、观察机制及退出行为并建立对照。

Session 由一个宿主串行使用，不同 Session 可由不同宿主线程操作。
取消请求支持并发，首版禁止与活动调用竞争销毁 Session。回调线程、可重入操作和注销完成点作为公开契约。

FramePool 使用拥有 WinRT 资源的 MTA 执行通道；PipeWire 遵循 thread-loop 的锁与回调纪律；Wayland 事件队列拥有者固定；macOS 完成状态独立保活。
P3 按[原生接口现代化清单](native-interface-modernization.md)迁移 FramePool 至 CreateFreeThreaded、PipeWire 至绝对时间等待，并接入 ExtImage；新入口不会取消既有线程/所有权纪律。FrameArrived 如启用，由内部工作线程通知，不能直接假定可在该线程访问全部 WinRT 资源；事件唤醒优化仍按 P6 单独评估。
采用 Rust 同步原语或后续执行器集成时仍保留这些约束：原生线程身份不能用任务身份代替，系统回调只更新允许的状态/通知，不从未知回调线程进入未经验证的调度等待；跨线程句柄与状态按实际 `Send`/`Sync` 约束封装。
原子操作、内存序和平台等待原语显式配对。用户回调及日志接收器在全局协调锁之外调用。

阶段三还需保证宿主线程环境：不修改进程级 DPI 设置，不把已初始化的宿主 STA 强行改为 MTA。
临时线程 DPI 上下文在成功、失败、取消和回调重入路径恢复；COM/WinRT 初始化仅配平本库成功取得的引用。
宿主回调的线程与 DPI 上下文明确约定，不能依赖测试入口已经初始化为本库期望的状态。

WindowCoordinator 在一份已加载模块内共享，同模块多个 Runtime 协调同一窗口身份：

1. 首次修改前记录样式、layered 属性和显示状态；多个租约共享原状态。
2. 恢复仅处理本库拥有的位和属性，保留宿主或窗口所有者的无关修改。
3. 校验窗口身份与生命周期；目标销毁或代次失效后停止对该对象恢复。
4. 独立观察伪最小化目标激活，暂停取图期间仍可恢复；目标成为前台时认可恢复意图。
5. 记录恢复冲突和失败，维护有界恢复状态，并提供可观察的退出结果。

注册表锁只定位状态，Win32 调用、回调和线程 join 在注册表锁之外执行。
窗口锁、同步消息、线程退出和宿主 UI 消息循环画出等待关系；宿主 UI 线程和独立宿主线程分别通过停机原型验证。
跨进程或独立加载的其他模块实例之间的窗口所有权由宿主协调。

独立激活观察在需要恢复的共享状态存续期间工作，不依赖再次调用截图或状态查询。
恢复判据不默认附加“必须有新输入”或恢复前台快照过滤；如需改变，先有误判复现、因果对照和独立决策。
观察器共享及事件/轮询选择不能削弱该行为；记录实际观察与恢复延迟，不把调度周期当作硬实时承诺。
锁的可重入性按真实调用图和等待关系确定，不因统一风格批量替换锁类型，也不能只依赖运行测试判断锁顺序安全。

## 执行与销毁关系表

下表是各后端设计和原型必须补齐的责任表，不表示统一线程实现已经完成。P0/P1 记录上游实际关系，P3 再落实 SDK 调度和退出契约。

| 后端 | 原生资源访问归属 | 回调允许的工作 | 停止与晚到结果责任 |
| --- | --- | --- | --- |
| GDI（窗口及 P3 全虚拟桌面扩展）/ ScreenDC / PrintWindow | 按迁移调用链和 DC/窗口线程要求；产品路径明确宿主线程与执行通道关系 | 仅进入已验证的窗口观察或同步消息路径；全虚拟桌面方式无窗口 helper | 保持返回后检查能力；清理 DC/位图并完成所需窗口恢复，不能宣称可中断 BitBlt 或 PrintWindow；全虚拟桌面资源流程见[专门设计](gdi-virtual-desktop.md#资源与执行责任) |
| FramePool / D3D / DXGI | 按对象约束访问；FramePool 由拥有 WinRT 资源的 MTA 通道操作 | 通知、取得允许的证据及更新独立完成状态；不越过线程约束 | 先停止新入口，按原生契约撤销事件并确认在途回调结束，再关闭资源与 context |
| PipeWire | thread-loop 所需锁内访问关联对象，停止 loop 不持该锁 | 更新流/格式/错误状态，取得样本并正确归还 buffer | 终止等待、归还所有 buffer，确认回调结束，再释放对象与初始化引用 |
| Wlr / ExtImage / Wayland | 固定事件队列拥有者，明确连接与分发责任 | 按各自协议推进请求，不意外分发宿主队列 | read/cancel-read 配平，完成代理/映射清理；ExtImage 的 session/frame、约束变化和 stopped/failed 分别处理，断连与取消路径均回收所有权 |
| ScreenCaptureKit | 按框架对象、回调队列及宿主事件循环要求访问 | 独立完成状态持有结果或错误 | 取消/超时后完成状态继续保活；晚到结果只清理，在途请求仍计入额度 |
| Custom provider | 由注册契约声明调用与释放线程 | 只执行允许的重入入口 | 所有权接管后成功/失败均恰好释放一次；注销包含在途调用排空 |

每项原型同时记录创建者、访问者、销毁者、同步等待者、注销完成证据和最终释放点。不能把“撤销注册调用返回”统一解释成所有原生 API 都已经排空回调。

## Session 迁移与可共享对象

宿主串行调用与固定线程是不同约束。P3 对每类 Session 明确是否可在相邻调用间迁移宿主线程、是否通过内部固定通道代理，以及关闭/析构应在哪个通道执行；具体 Rust Send/Sync 实现依据这些证据确定，不先统一声明所有 Session 可移动。

可变会话操作在 Rust 安全 API 中采用独占访问语义；C ABI 另行验证忙状态和重入。不可变 CPU Frame 与独立取消句柄按自身所有权证明跨线程条件，不能继承 Session 或原生资源的线程安全结论。

## 退出与锁的验证材料

各后端维护停止顺序与等待关系：停止新请求、处理当前操作、撤销事件入口、接管晚到资源、确认在途回调结束、释放 context/原生资源、完成窗口恢复。原生 API 要求不同顺序时逐项记录，不强行套用同一清理函数。

锁图标出会话锁、窗口注册表、单窗口状态、原生 loop 锁、同步消息、线程 join 与宿主 UI 循环。用户回调在协调锁之外执行；在回调中不能同步等待自身排空。close 的可观察结果区分主要失败、清理失败和仍在途/待恢复责任，Drop 只执行已定义兜底。

公共生命周期见[生命周期设计](../contracts/lifecycle.md)，回调允许的重入入口见[C ABI 与回调设计](../contracts/c-abi.md)。
