## 1. 项目定位与目标

**maafw-screencap** 是首选使用 **Rust** 实现的独立桌面截图库，先完整迁移固定版本 MaaFramework 的截图实现，再应用指定修复，最后建设独立 SDK 和扩展能力。
核心协调、状态、策略、帧管理和后端流程使用 Rust；对外动态链接边界采用 C ABI。
平台接入优先采用维护活跃的 Rust 原生绑定；必要的 C、C++、Objective-C/Objective-C++ 代码仅承担原生 API、协议宏或验收适配的窄桥接职责。

最终 SDK 的首选方案为：**捕获核心及 binding 的基础捕获路径不依赖 OpenCV，通过 C ABI 交付自描述、独立持有的原格式 CPU Frame；各语言提供薄适配，按需复用调用方已有 OpenCV/图像框架完成转换，首版不交付独立共享转换模块**。
核心保留原生捕获、目标范围校验、必要复制及帧生命周期；复杂预处理、用户算法 ROI、模板匹配和机器学习由调用方负责。
该方案在阶段三沿已验收的迁移实现落实；阶段一、二由 Rust 捕获实现与最小验收 binding/适配器共同兑现上游 OpenCV 转换语义和输出行为，不要求核心直接链接 OpenCV。

项目使用独立仓库、构建、版本、包与发布流程，继承上游 LGPL 许可，采用 `LGPL-3.0-or-later`；许可与分发要求见第 3.3 节。
后续优化和修改优先基于阶段一完整迁移得到的 Rust 代码：阶段二在其上独立应用指定 PR，阶段三沿同一代码主线增量演进。
像素、选源、默认值、等待/回放、生命周期及窗口副作用优先保持固定上游行为；仅当新行为有明确的最佳实践依据时才改变，并单独记录理由与验收证据。
新增 SDK 契约与内部整理不自动要求改变原生捕获行为，架构重组或性能偏好本身不构成行为变更理由。
系统能力及其他功能实现优先使用适合本项目的 Rust 标准库、语言与 Cargo 构建能力；默认跟进最新 nightly，标准库实验分配 API 集中在必要的内部封装，具体约束见第 5.1、8.2 节。原生 ABI 的必要调用保持明确边界，不重复维护标准库或成熟绑定已经解决的通用适配。
语言选择围绕原生捕获性能、所有权、回调线程、FFI 可验证性和维护成本，OpenCV 调用由 binding/调用端承担，其 Rust 绑定成熟度不作为核心语言的降权因素；不预设语言本身带来更高帧率或更低资源占用。

项目目标包括：

1. 完整迁移固定上游的全部桌面截图后端、直接辅助实现和截图调用链，验证像素、默认值、资源生命周期与副作用。
2. 在完整迁移基线上独立应用 [PR #1587](https://github.com/MaaXYZ/MaaFramework/pull/1587) 的最终修复，并验证修复前后差异。
3. 在补丁基线上提供目标身份、原格式帧与可选转换、帧所有权、生命周期、错误、能力查询及 SDK/绑定。
4. 在正确性与可复核测量基础上增加策略、异步能力和性能优化。

### 1.1 固定实施顺序

| 顺序 | 里程碑 | 范围与前置条件 |
| --- | --- | --- |
| 阶段一：完整上游迁移 | 未附加 PR 修复的 Rust 基线 U | 准备固定来源和工具链，完整迁移全部截图实现及直接辅助/调用路径，保持上游可观察行为并完成对照验收 |
| 阶段二：PR #1587 修复 | 基线 U + 固定补丁得到基线 P | 阶段一完成后，仅加入 PR 最终差异并验收；参考程序和 Rust 实现使用相同补丁语义 |
| 阶段三：SDK 与扩展 | 在基线 P 上逐项形成产品能力 E | 阶段二验收通过后，依次实现独立核心契约、正确性增强、策略、绑定/分发及经测量的优化 |

阶段一、二各自保留可重建的源码快照、构建清单和测试结果，全部存放在项目同级的独立参考目录。完整迁移覆盖所有平台后端，不能以某个平台或单个后端完成代替该里程碑。
阶段一只做 Rust 语言、原生 ABI、构建和最小验收调用所需的适配；默认方法、选源、像素转换、等待/回放、窗口调整及其他副作用以固定上游为准。
验收适配采用已选定的 C++ + OpenCV，通过必要的私有窄 C 边界接入并按上游操作顺序执行转换；捕获实现与适配器合并作为 U/P 的行为对照对象。转换位置影响失败、缓存、时序或资源寿命时，在原调用位置接入适配或证明等价，不能仅凭最终像素相同判定通过。
PR 修复单独进入阶段二；共享租约、严格目标/几何拒收、新鲜度、总期限等额外设计统一进入阶段三。
公开原格式输出及调用端转换契约属于阶段三；U/P 可使用内部原格式交接和验收适配，但必须验收完整的上游统一输出，不能以原始帧成功交付代替上游 BGR 行为已验收。
第 6–15、17–18 节描述最终产品设计，其完整契约在阶段三落实；前两阶段使用最小测试/调用入口，不提前冻结最终 SDK 或加入扩展行为。

公共 API 围绕截图会话设计。输入控制、ADB/Android、PlayCover、识别/OCR、任务流水线、Agent、录制回放及 Qt 应用逻辑不在范围内。
PipeWire Portal 的来源授权由宿主提供，或通过单独定义的授权接口协作；授权、来源选择和截图失败恢复分别建模。

## 2. 平台范围与交付层级

首批构建目标为 Windows x64、Linux x64、macOS arm64。其他架构通过独立构建、ABI 和原生环境验收后加入。
首批 Windows Rust target 使用 `x86_64-pc-windows-msvc`；C++ 验收及 OpenCV 与其核对架构、ABI 和运行库配置。首版 Windows 原生验收仅实现 VS2026 + MSBuild，VS2022 与 MSVC-Ninja 在后续版本扩展，详见第 5.7 节。
每个平台分别报告“可构建”“可加载”“通过原生桌面场景”，支持声明附具体 OS、SDK、驱动和显示环境。
性能评估以 Windows 单目标持续捕获为主要场景，优先低延迟与高帧率，允许经测量的适度 CPU/内存投入；同时优化 Linux/macOS，保持三平台独立验收，不预设未经测量的性能上限。

| 平台 | 计划后端 | 目标与边界 |
| --- | --- | --- |
| Windows | GDI、ScreenDC、PrintWindow、FramePool、DesktopDup、DesktopDupWindow | 窗口或显示器；按方法表达客户区、可见桌面限制、前台操作与伪最小化行为 |
| Windows 产品扩展（P3） | 独立 GDI 全虚拟桌面方式，工作名 GdiVirtualDesktop | 当前可访问桌面的活动逻辑显示区域包围框；屏幕 DC 一次取图，发布独立原始 CPU Frame；尚未实现或验收 |
| Linux | PipeWire、Wlr screencopy；P3 新增 ExtImage | 已授权 fd/来源标识或指定 Wayland 输出；U/P 保持原 node ID/Wlr 路径，P3 按原生接口清单迁移目标选择并接入 ExtImage，尚未实现或验收 |
| macOS | ScreenCaptureKit | 指定窗口或显示器；明确权限、point/pixel 比例、过滤范围和异步完成语义 |
| 平台无关 | Custom provider | 宿主注册回调提供像素和来源声明，元数据标明 provider 证明范围 |

平台范围不表示每个后端都支持该平台的全部目标。P0 按固定源码列出“方法 × 目标类型”的实际支持矩阵，随 U/P 对照记录存放在同级参考目录。
P3 将已实现组合、运行时条件、画面范围和限制表达为产品能力；原生 API 理论上可支持的其他目标作为独立扩展，不自动算入完整迁移或首版支持。

GDI 全虚拟桌面已按 [ADR 0001](../decisions/0001-gdi-virtual-desktop-capture.md)纳入 P2 后 P3 的独立产品扩展，不计入 P0/P1 的上游六种 Windows 方法或 P2 补丁范围。具体方法、目标类型、能力值与 ABI 在 P3 定案，发布须完成本节支持声明及第 14 节验收；本扩展不同时承诺逐屏合成或其他平台的全虚拟桌面路径。

首批接口交付 Rust crate/API、C ABI、C++ RAII 包装及 Python 绑定。
首版 Python 验证采用 ctypes + 公共 C ABI，后续版本迁移为 PyO3 + maturin；首版 Rust 源码 crate 与 Python binding 随 GitHub Release 的 SDK/配套资产交付，语言公开包渠道在后续版本启用，详见第 15.2、15.7 节。
Node.js、Zig、Go、Java、C# 按实际消费者需求逐项加入；异步流接口和损伤区域接口作为后续扩展。

### 3.2 参考与产品的关系

独立参考程序用于确认上游的像素、默认值、资源生命周期、时间及副作用。
Rust 产品按职责实现后端和公共契约；原生桥接只封装必要边界，核心状态机和捕获策略由 Rust 管理。
每项与参考不同的行为说明原因、影响、分类和验收证据；安全要求与产品契约在对应后端发布前落实。
阶段三以已验收的迁移实现为基础，先考虑保持行为的局部改进；只有原生 API 约束、内存/线程安全或更明确的公共契约等依据足以支持时才采用新行为。
行为改变需要说明上游行为、实际问题、候选方案、最佳实践依据、默认值影响和验证结果；不能仅因实现便利重新定义行为。
阶段一参考程序保持固定上游未打补丁状态，Rust 基线 U 与其逐项对照；阶段二另建附加 PR 的参考基线，与 Rust 基线 P 对照。
阶段三每项变化以基线 P 为起点单独验证，保留与 U 的关系。前两阶段是内部工程验收基线，正式 SDK 发布使用完成产品契约验收的产物。
原格式路径按实际取样格式验收；与上游统一像素输出的对照通过明确的转换适配形成相同格式后执行，并分别报告核心原始输出和转换结果。

### 3.5 行为保持与优化决策

| 变更类型 | 实施原则 |
| --- | --- |
| 语言适配、模块整理与原生互操作 | 优先保持行为；后续实现沿完整迁移代码演进，必要桥接仍保持窄边界 |
| PR #1587 | 在迁移实现上独立应用固定最终差异，保持补丁之外行为 |
| 正确性和安全增强 | 先确认问题与触发条件；行为变化须有最佳实践依据及针对性回归，不批量替换已有流程 |
| 策略和 SDK 能力 | 尽量采用增量描述与显式选项；默认行为沿用上游，确需改变默认值时单独决策并记录理由 |
| 原生接口现代化 | 按 ADR 0002 在 P2 后逐项迁移旧兼容用法及清单内有效接口；核验格式、来源、线程和最低能力，兼容调用条件明确，不把依赖更新等同已迁移 |
| 性能优化 | 在相同画面、来源和副作用约束下测量；收益不能以未声明的行为变化换取 |

第 6–15、17–18 节是阶段三的设计与验收起点；其中改变上游行为的条目均按上述原则形成独立决策。
公共 API 可以建立独立契约，后端不因此被默认重写；实现与上游的关系持续通过职责映射和行为对照验证。

原生接口现代化已按 [ADR 0002](../decisions/0002-native-interface-modernization.md)纳入实施，范围与门禁见第 11.7 节；这是 P2 后的产品变更，不提前替换 U/P 的原生接口或转移转换调用点。

阶段三的正确性要求、可选产品能力和待测量优化分别管理：内存/资源/错误正确性是放行条件；产品能力按需求开放，开放后必须完整兑现；性能方案先评估，不预先承诺一定采用。
每个方案按具体行为和实现边界判断，不能因其所在提交或某组代码包含安全修复，就连带接受其中的其他行为变化。

### 3.6 不采纳的实现与默认行为

以下是禁止作为优化保留的模式及其替代要求，不属于计划实施项；同级参考目录另存逐项取舍依据，产品仓库不包含提交对照或来源映射。

| 不采纳的模式 | 实施边界 |
| --- | --- |
| 删除独立激活观察，仅在后续截图/查询时恢复；额外要求新键鼠输入或以前台快照排除恢复 | 保持无新输入的程序激活也可恢复；共享状态与安全退出不能以削弱恢复行为换取 |
| 为去依赖直接替换转换公式，改变 YUY2 范围/矩阵，或用大容差掩盖像素差异 | U/P 保留固定转换；替换逐操作对照，未等价不接管 |
| 将回放标为新样本、以交付时间冒充取样时间、用新格式描述旧缓冲或允许可写帧污染缓存 | 按第 8、10、12 节落实样本、代次和所有权契约 |
| 删除映射/归还回调前的必要复制，或用全局 TTL 快照代替独立来源复验 | 先证明寿命、隔离与验证等价，再测量优化；必要边界不得删除 |
| 只做返回后检查却宣称可中断等待，或用库级功能位宣称全部方法支持同一策略 | 区分入口存在、方法/目标支持及实际等待能力，不能承诺未实现的强保证 |
| 将共享状态视为任意并发安全、忽略清理失败继续试用候选，或用自动重试掩盖真实断言失败 | 保留串行宿主边界、候选隔离、可观察失败和针对性回归 |
| 无独立理由改默认回放、将 pause 变成销毁、固定方法静默换法，或暗改测速次数/顺序 | 新操作或策略显式表达；默认变化仍按第 3.5 节独立决策，不能以整理或优化名义混入 |

默认禁止回放、资源释放接口及更严格的来源/几何保证并非一概不合理；是否采用取决于明确需求、最佳实践依据和验收，不能单凭“不同于上游”或“能力更多”判断优劣。

## 5. 工具链、依赖与原生互操作

### 5.1 Rust 工具链

主构建入口为 `Cargo.toml`，必要的原生编译、探测与声明生成由 `build.rs` 集成；SDK、跨语言消费和对照任务由 workspace 内的轻量 `xtask` 编排。xtask 不直接或间接依赖捕获 crate，使准备任务可在后端尚不可构建时运行；构建责任和显式配置产物见[开发指南](../guides/development.md#构建责任与启动顺序)。
开发脚本、产品构建与 CI 通过 rustup 跟进最新 `nightly`，使用该工具链支持的适用 edition，并安装匹配的 rustfmt/Clippy；`rust-toolchain.toml` 的 channel 使用 `nightly`，不写入精确工具链版本。实际工具链身份作为该次构建记录保存，不作为未来版本锁定。
优先使用已有稳定标准能力；必要的 fallible 对象分配采用标准库实验 API，并集中在内部所有者封装。当前 [nightly 文档](https://doc.rust-lang.org/nightly/std/boxed/struct.Box.html#method.try_new)中的 `Box::try_new`、`Arc::try_new` 使用 `allocator_ext` feature gate，实际构建前核对接口及 gate，不将分配器接口的部分稳定化视为全部 fallible API 已稳定。
Rust 源码消费者需要 nightly；不维护额外 stable 分配实现，不以 `RUSTC_BOOTSTRAP` 绕过工具链要求。相关 API 全部稳定且迁移通过验收后，移除对应 gate 并将默认工具链迁回 stable；其他实验能力逐项说明必要性，不因使用 nightly 自动扩大范围。正式 SDK 公共接口仍在 P2 验收后设计。
P0 按第 15.5 节完成本机本地及三平台 Actions 最小互操作原型，覆盖原生取帧、独立持帧、回调停止、FFI 和可恢复分配失败；更新工具链后重跑受影响验收。
包依赖、系统 SDK、外部编译器和运行库按第 5.6 节跟进最新版本，实际构建记录写入同级参考目录。

Windows 采用 Microsoft 维护的 [`windows-rs`](https://github.com/microsoft/windows-rs) 生态专用 crate，并使用 `windows-bindgen` 生成所需的项目私有 Win32、COM 与 WinRT 绑定；具体覆盖与生成参数在 P0 验证。Linux/macOS 按第 5.3 节使用对应 Rust 绑定或必要的窄桥接。
已有维护活跃且覆盖所需 ABI 的绑定时优先复用；需从 C 头生成声明时采用 allowlist 限定的 bindgen，记录头文件、target、宏、include、生成器及 clang 参数，生成声明与手写安全封装分开管理。
生成结果放入构建输出目录，CI 验证布局、调用约定、符号及链接；公共 C 头继续是第 7.2 节的 ABI 契约来源，不把整个系统 SDK 重新生成到产品源码中。
工具链、绑定和生成器升级分别说明影响并重跑受影响的 ABI、内存、并发、消费与分发验收；Rust 工具链的稳定性承诺不代替第三方 crate 更新验证。
构建与互操作以 [Cargo 文档](https://doc.rust-lang.org/cargo/)、[Rust Reference](https://doc.rust-lang.org/reference/) 及实际解析依赖的维护者文档为依据。

### 5.2 图像职责、可选 OpenCV 与基础依赖

参考程序与阶段一、二的验收 binding/适配器采用最新正式版 OpenCV，按上游 `core`/`imgproc` 操作、参数和顺序兑现颜色、裁剪及输出语义，不据此冻结依赖版本。
U/P 的 OpenCV 默认从最新正式版源码构建，明确上游实际所需模块及其依赖，保留所用操作对应的 CPU baseline/dispatch、SIMD 和适用 HAL/第三方优化；记录来源、实际版本、编译器、运行库、模块、选项和优化能力。按实际解析身份与配置复用缓存，同次 U/P 参考与 Rust 验收适配使用一致的实际依赖集合；不将来源不明的预装库作为默认替代。该源码构建只属于显式对照/验收准备，不进入产品基础构建。
U/P 的对照入口组合 Rust 捕获实现与 C++ + OpenCV 最小验收适配器，沿上游 `cv::Mat` 和转换调用顺序验证输出、失败与生命周期；适配器通过必要的私有窄 C 边界接入，不以 Rust OpenCV 绑定成熟度限制主体实现。
原生句柄、映射、缓冲归还、目标范围处理和捕获状态仍由捕获实现负责；不能把借用的失效缓冲交给适配器，也不能因转换后移改变失败、缓存、等待/回放或资源寿命而未记录。
确需保持原调用时点时，可在该位置调用验收适配，必要桥接仅限对照目标；`cv::Mat`、STL、语言异常及适配器对象不跨公共 C ABI，不形成产品共享转换库。
P3 在同一基线 P 上建立正式原格式与调用端转换契约，以无 OpenCV 依赖的核心和基础 binding 作为首选交付；不要求为去依赖把全部转换 kernel 重写为 Rust。

| 职责 | 首选归属与边界 |
| --- | --- |
| 原生捕获、映射、同步、缓冲归还和独立 Frame | 核心；原生有效期内完成必要复制或可证明的所有权接管，接口不暴露已失效地址 |
| 目标客户区提取、来源/几何与长度校验 | 核心；用 Rust 基础内存与矩形操作落实范围隔离，不能交由 binding 遮蔽目标外像素 |
| 像素格式、stride、方向、alpha、颜色及样本元数据 | 核心如实描述；已知、未知及不支持分别表达，不能仅以通道数解释缓冲 |
| BGR/RGB 等消费者格式转换 | 各语言薄适配或调用方；通过现有 OpenCV/图像框架的公开 API 执行，不在首版增加共享转换运行库 |
| OpenCV Mat、NumPy 数组及框架输入视图 | 对应 binding 的可选适配；视图持有 Frame，写入与复制契约明确 |
| 用户算法 ROI、缩放、归一化、复杂预处理、模板匹配及推理 | 调用方；不因适配 OpenCV 将完整算法流水线纳入捕获核心 |

首版各语言 binding 随包提供必要的薄适配代码，转换 kernel 使用调用方已有图像库；不附带 OpenCV 二进制，也不将共享原生转换组件列为 SDK/wheel 的交付项。
Python 适配使用当前环境 `cv2` 的公开接口；C++ 适配以源码/可选头形式接入调用方 OpenCV；Rust 的可选图像适配使用对应生态绑定及其经核验的原生安装。Rust 图像适配置于 binding 侧独立包或调用端源码，OpenCV crate 不进入捕获核心 crate 的依赖树，适配测试显式选择。纯 C/Zig 消费者直接使用原始帧，或自行对接图像库/转换实现。
各生态安装不等同于通用原生 SDK：不能假定 Python 的 `cv2` 包可直接供其他语言链接，也不从第三方包内部提取私有 ABI 使用；公共核心 ABI 不暴露 OpenCV 类型。
binding 可以提供转换入口和能力查询，但转换依赖不存在、版本不兼容或格式不支持时明确失败；原始捕获仍可独立使用，不承诺无转换实现时自动得到 BGR/RGB。
基础导入、安装和捕获不强制下载、加载或替换 OpenCV；所需依赖遵循第 5.6 节，由调用方显式准备满足要求的环境，适配核验版本与实际能力。
原生截图桥接自身所需 C++ 运行库等依赖另行判断，不能宣称移除 OpenCV 后全部 C++ 依赖自动消失。

色彩范围/矩阵、取整、饱和、alpha、stride、ROI、方向、失败路径和生命周期逐项对照；色彩语义差异与舍入差异分别验收，不能用统一像素容差掩盖变化。
启用的适配保留实际使用操作对应的 SIMD、CPU 特性分发及适用 HAL/第三方优化，不以标量等价或编译器可能自动向量化代替覆盖证明。
自有转换仅作为有明确收益的后续候选；采用前须同时通过像素、安全、支持平台及对应优化覆盖/性能验收，不将补回既有加速推迟到替换完成之后。
转换位置按第 18 节比较完整消费链路；原始帧方案不预先承诺减少总复制或提高所有消费者的帧率。共享转换或原生融合仅按第 8.5 节触发条件另行评估，保持基础构建无 OpenCV 依赖。
日志、时间、受检算术和资源清理由 Rust 实现，分别验证时钟、同步、错误及清理契约；通用复制、切片、数值与容器优先使用 Rust 安全接口，分配和地址稳定性按第 8.2 节单独设计。

### 5.3 平台互操作

| 平台 | 实现要求 |
| --- | --- |
| Windows | 通过 `windows-rs` 专用 crate 与 `windows-bindgen` 私有投影按需接入 D3D11、DXGI、DWM、Win32/GDI、WinRT/COM 和缩放接口；验证 GUID、HRESULT、调用约定、引用计数和事件注销。直接使用 Rust 投影接入 FramePool 等能力，不默认增加 C++ 层；声明缺口确需补充时提供仅包装原生边界的私有桥接 |
| Linux | 探测 PipeWire、libdrm、wayland-client；优先采用 `pipewire` 与 `wayland-client` 高层绑定，显式启用 `wayland-backend` 的 `client_system`，使 U/P 沿用系统 libwayland 路径；必要语义未覆盖时局部使用 sys 绑定或最小 C shim。保持 thread-loop 锁、队列和 fd 所有权纪律；切换协议实现需证明等价。协议 XML/scanner 与声明生成分别记录输入并验证时序和 ABI |
| macOS | 通过 `objc2` 及 ScreenCaptureKit、AppKit、CoreMedia/CoreVideo/CoreFoundation 等框架绑定直接接入，按需使用 `block2`、`dispatch2`；验证实际所需对象、block、完成回调与运行时可用性。明确 retain/release、autorelease pool 和回调保活；仅为已证明的缺口使用最小 Objective-C 桥接，确有需要时使用 Objective-C++ |

每项桥接记录职责、编译器、运行库、C ABI 和替换条件。
SDK 编译能力与运行时 API 能力分别探测。后端开关采用 AUTO/ON/OFF：准备入口在调用 Cargo 构建产品前完成探测并选择本机 feature/构建配置，AUTO 可禁用缺依赖后端并报告原因，显式 ON 缺依赖时失败；`build.rs` 复验已选择配置，不依赖其事后关闭已经选择的 Cargo 依赖。
Rust 源码消费者通过显式平台 feature 声明所需后端；AUTO 选择由准备/SDK 入口提供，直接 Cargo 消费的 feature 与缺依赖失败规则单独说明。
运行时请求未编入或当前环境不支持的能力返回明确错误。Cargo feature 仅增加可编入能力；AUTO/ON/OFF 在准备入口解析，方法/策略在运行时选择，不使用互斥的 U/P/E feature 切换行为。

### 5.4 Rust 标准能力、安全封装与执行模型

采用顺序为：能满足语义的 Rust 安全标准抽象 → 维护活跃的原生绑定及局部安全封装 → 必要的底层 FFI/窄桥接。选择后两者时记录标准抽象缺少的语义与验证依据，记录保存在同级参考目录。
核心状态、策略和布局处理优先保持安全 Rust；`unsafe` 限于经核验的指针访问、FFI、所有权接管和必要底层操作，每处说明有效期、别名、线程与释放不变量，启用 `unsafe_op_in_unsafe_fn` 等适用检查。
原生绑定提供声明和部分对象管理，不自动证明外部缓冲有效、目标隔离、线程安全或退出排空；这些仍按公共契约和平台测试验证。

| 职责 | 优先实现与边界 |
| --- | --- |
| 文件、路径、日志输出、临时文件和工具进程 | 优先 `std::fs`、`std::path`、`std::io`、`std::process` 及维护活跃的必要工具 crate；库通过显式配置接入，不擅自安装进程级日志接收器或修改宿主全局环境 |
| 时钟、等待、同步及后台任务 | 优先 `Instant`、标准同步原语和后端所需原生事件/循环；显式管理绝对 deadline、错误唤醒、取消状态、操作代次和任务收束 |
| Windows 系统能力 | 优先使用适用标准接口及 Microsoft 原生绑定；保留 COM apartment、DPI 和事件纪律，不为追求更底层而硬编码 syscall 或复制未公开系统实现 |
| GDI/D3D11/DXGI/WinRT、PipeWire/Wayland、ScreenCaptureKit | 通过对应平台绑定调用；通用异步执行器不能替代协议队列、权限、映射、producer 同步及固定线程身份 |
| 内存、容器与数据处理 | 明确对象、帧存储和回调状态的所有权；适用处采用切片、RAII、受检算术和标准容器；可恢复分配失败与稳定地址按第 8.2 节核验 |
| 像素布局与可选转换 | 核心优先安全切片复制、受检算术及矩形操作；颜色转换按第 5.2 节由可选适配/调用端处理。自有 kernel 需在接管前兑现原有优化覆盖，P6 再评估额外 SIMD 优化 |

首期不要求 Tokio、async-std 或其他通用异步运行时；按后端使用所需原生线程/事件模型，不为统一接口而默认增加每帧任务分派和线程切换。
Runtime 管理共享协调与必要执行状态，原生资源按所属执行通道访问；按实际需要共享 Frame/完成状态，避免无条件将全部状态组织成 `Arc<Mutex<_>>`。
Rust 源码消费者无需预先建立执行器，C ABI 不暴露 Rust executor、trait object、标准库对象或 allocator 布局；若后续提供执行器集成，单独定义借用寿命与线程约束。
系统回调仅更新允许的状态和通知，注销与在途回调排空后才能释放 context；`Send`/`Sync` 以真实对象约束为依据，不以手写不安全实现绕过原生线程限制。
取消请求不保证中断原生调用；取消与成功完成竞争时仍接管并清理已产生资源，恢复与资源归还不能因取消而被跳过。
P0/P1 可使用不改变行为的现代语言/标准库适配，保持上游调用顺序、观察、等待/回放与窗口副作用；更换调度、扩大并行、改变取消/期限或增加流接口仍在 P3–P6 单独实施。

### 5.5 依赖调试与包目录

依赖调试优先采用 Cargo 支持的 path/`[patch]` 覆盖，配置放在明确启用的外部调试环境；引用项目同级工作目录，不把普通参考源码误作可替换 crate。
临时覆盖不改写正式最新版本解析规则；正式资产关闭覆盖，依赖修复优先进入维护者发布的最新版本，采用后重跑验证。
将 `CARGO_HOME` 的 registry/git 缓存和 `CARGO_TARGET_DIR` 构建输出指向同级 `maafw-screencap-deps/` 下的独立子目录，与参考资料目录分开；按实际解析依赖、工具链、target、feature、profile 和原生选项区分构建缓存。
可复用下载和原生依赖构建缓存同样写入 `maafw-screencap-deps/`，不在参考区另设通用 `dependencies/` 缓存。该次构建的解析清单、Cargo.lock 和需保留的离线重建快照进入 `maafw-screencap-reference/runs/<run-id>/inputs/`；缓存可清理，已验收基线与发布记录所需的快照独立保留。
准备入口统一解析最新工具链与依赖；缓存恢复不跳过更新检查，不能把已存在的解析文件直接作为下一次在线构建的固定输入。
离线重建使用该次构建已准备的依赖快照和系统 SDK，相关解析记录保存在外部工程目录；不将其作为后续在线构建的版本约束，干净消费不借用参考目录。

### 5.6 依赖选型与最新版本策略

依赖优先选择现代化、高性能、主流且维护活跃的方案，结合实际平台覆盖、许可证、维护频率、接口质量与基准结果判断；有满足需求的 Rust 标准能力时优先使用。
本策略覆盖直接与传递依赖、参考程序依赖、绑定与生成器、构建/测试/打包工具、系统开发依赖及 GitHub Actions Workflow 中使用的 Marketplace Action。

所有依赖均跟进最新正式版，不锁定精确版本号、提交 SHA 或指向特定版本的下载地址；没有正式版的必要依赖使用维护者活跃维护的分支，并记录实际解析身份。
Rust/Cargo 工具链为明确例外，按第 5.1 节跟进 nightly 以使用所需标准库实验分配 API；该选择不将其他依赖默认切换为预发布版本。Windows 原生工具链首版按第 5.7 节采用 VS2026，后续扩展 VS2022 兼容配置；各已实现配置跟进对应产品线的可用正式更新，实际版本记录不作为精确锁定。
声明与获取入口采用维护者支持的浮动版本标识或构建前的最新版本解析；不假定所有生态都提供 `latest` 标签，也不以只允许旧主版本的范围长期阻止升级。
Marketplace Action 使用维护者提供的最新正式版主版本标签（如 `@v<当前主版本>`），不使用精确补丁标签或提交 SHA；出现新主版本时及时更新 Workflow 并验证行为。

构建准备步骤解析最新版本；包管理器必须使用内容寻址或解析文件时，先刷新相应数据再构建，不将历史解析结果作为仓库中长期冻结依赖的依据。
Cargo 依赖使用可更新的兼容范围；准备入口还需检查范围外的新正式版并及时适配，不能只执行 `cargo update` 就宣称已经跟进最新主版本。`Cargo.lock` 只记录该次解析并用于同次构建/离线重建，归档到外部 `runs/<run-id>/inputs/`，不提交为长期版本锁定；crate 发布时核验清单满足 registry 规则。
下载校验值继续用于完整性检查。实际版本、提交和哈希只作为该次构建与离线重建的记录，保存在外部工程目录，不反向成为未来构建的版本约束。
缓存按实际解析身份区分，恢复缓存不能跳过最新版本查询；更新后重跑受影响的原生互操作、ABI、像素对照与分发消费验收。
最新版本出现兼容性问题时，优先适配或重新选型，未解决则报告验收受阻，不能默默退回并冻结旧版。运行时最低 OS/协议能力要求与构建依赖版本分开定义。

### 5.7 原生验收构建与 Windows 工具链

独立上游参考程序与 C++ + OpenCV 验收适配使用 CMake，生成器按平台选择，具体工具组合由 `xtask` 准备和编排。Rust 产品仍由 Cargo 构建；必要小型原生桥接由 `build.rs` 集成，不把 CMake 变成与 Cargo 重复的产品构建入口。

首版 Windows 原生验收仅需实现已安装的 VS2026 + MSBuild 路径，使用 CMake 的 `Visual Studio 18 2026` 生成器、x64 架构，并通过 MSBuild 编译生成参考程序、C++ 验收适配及对应原生依赖。VS2022 和 MSVC 环境下的 Ninja 保留为后续扩展，不要求首版实现或纳入首版 Windows 必需验收矩阵。

| 配置 | 交付阶段 | CMake generator | 环境与构建要求 |
| --- | --- | --- | --- |
| VS2026 + MSBuild | 首版实现与验证 | `Visual Studio 18 2026` | 选择已安装 VS2026 实例、`-A x64`；要求相应 MSBuild/MSVC/SDK，不依赖 Ninja |
| VS2022 + MSBuild | 后续扩展 | `Visual Studio 17 2022` | 选择 VS2022 实例、`-A x64`；要求相应 MSBuild/MSVC/SDK |
| VS2022 + Ninja | 后续扩展 | `Ninja` | 先初始化所选 VS2022 实例的 MSVC x64 开发环境，明确使用 MSVC 编译器和链接器 |
| VS2026 + Ninja | 后续扩展 | `Ninja` | 先初始化所选 VS2026 实例的 MSVC x64 开发环境，明确使用 MSVC 编译器和链接器 |

首版配置入口定位 VS2026 实例并探测实际 MSVC 工具集和 Windows SDK；不将 VS 产品名等同于固定工具集版本。Visual Studio 生成器按需使用 `CMAKE_GENERATOR_INSTANCE` 指向所选安装。后续实现 VS2022/Ninja 选项时，再分别选择 VS 产品线和生成器；Ninja 继承对应实例通过 `VsDevCmd`/`vcvars64` 建立的完整开发环境，核对实际 C/C++ 编译器为所选 MSVC。开发机绝对路径仅保存在外部构建记录，不写入产品配置。

本机首版验证使用已经安装的 VS2026，仅覆盖 MSBuild 编译生成路径。后续增加 VS2022 或 MSVC-Ninja 时，在具备对应工具的原生环境独立验收。显式请求未实现的组合时报告不支持；已实现组合缺少必需组件时报告配置缺失，不静默换用其他组合。Linux/macOS 按实际平台和可用原生工具选择、记录 CMake 生成器。

各已实现组合使用独立构建目录；缓存至少区分 target/架构、VS 实例及实际 MSVC/SDK、生成器、profile/构建类型、运行库和依赖选项。首版 MSBuild 多配置目标在构建时选择 `--config Release` 等配置；后续实现单配置 Ninja 时再在配置阶段设置 `CMAKE_BUILD_TYPE`。CMake 跟进最新正式版，并验证所选生成器实际可用；VS2026 生成器的能力下限为 CMake 4.2，不将此下限当作依赖锁定。

生成器依据：[CMake VS2022](https://cmake.org/cmake/help/latest/generator/Visual%20Studio%2017%202022.html)、[CMake VS2026](https://cmake.org/cmake/help/latest/generator/Visual%20Studio%2018%202026.html)、[CMake 生成器与环境要求](https://cmake.org/cmake/help/latest/manual/cmake-generators.7.html)。

## 6. 架构与模块

### 6.1 职责分层

采用单一捕获 crate + xtask。基础模型、会话编排、内部策略决策、后端契约与平台资源封装保持明确的依赖方向；后端不反向控制 Session 或缓存，Windows 窗口协调留在平台模块。
模块职责、依赖图、核心对象、原生租约 → 独立 CPU BackendSample → Frame 的所有权交接，以及逐阶段演进规则以[架构设计](../design/architecture.md)为权威来源。具体公共 API 在 P2 验收后设计，U/P 保持原调用和转换时点。

### 6.2 项目目录

单一捕获 crate 的目标源码树见[架构设计：目标项目结构](../design/architecture.md#目标项目结构)，当前实际结构见[文档导航](../README.md)。使用 c_api 区分对外 ABI，原生声明/封装靠近平台后端；单元测试随模块，集成测试使用明确 Cargo target，跨语言任务由 xtask 编排。
生成输入、构建启动顺序、配置产物与测试入口见[开发与验证指南](../guides/development.md)。所有目录随阶段和实际内容建立，不预建空后端、桥接、manifest 或示例。

参考资料继续使用项目同级的独立目录。按“可清理缓存、不可覆盖的基线、同次运行证据、本机信息”划分，目录按实际阶段和任务需要建立：

```text
workspace/
  maafw-screencap/            # 产品项目及独立 Git 仓库
  maafw-screencap-deps/       # 按解析身份和配置区分的可清理缓存
    cargo-home/              # Cargo registry/git 缓存
    downloads/               # 可复用依赖下载
    native/                  # OpenCV 等原生依赖构建/安装缓存
    target/                  # CARGO_TARGET_DIR
  maafw-screencap-reference/  # 仓库外的基线、快照与工程证据
    manifest.json            # 布局版本和基线/补丁/运行批次索引
    baselines/
      u/<baseline-id>/       # 固定上游及未打补丁的独立参考程序
      p/<baseline-id>/       # 对应 U 加累计补丁的独立参考程序
    patches/pr-1587/
      1587.patch
      manifest.json          # PR 来源与累计补丁哈希
    runs/<run-id>/
      manifest.json          # 本批次实际输入、配置、结果路径和哈希
      inputs/                # 解析清单、源码/映射及必要依赖快照
      <platform-config>/    # 如 windows-x64-vs2026-msbuild-release
        reports/             # 单项结果、跨实现/基线对照与消费验收
        <variant>/           # reference-u、rust-u、reference-p 等
          build/             # 本次参考/验收构建工作目录，可重建
          artifacts/         # 需保留的程序、帧及其他验收产物
          logs/
    local/
      observations/          # 本机工具与消费者检查记录
      consumers/             # 本机消费者路径与验收配置
```

每个基线目录包含 `manifest.json`、`reference/`（独立参考程序及所需源码/适配快照）、`mappings/` 和 `audits/`（来源差异、行为对照决策与许可核验）。基线 ID 绑定确定的输入身份，P 显式引用父 U；原始源码与构建适配分别记录，不就地给 U 打补丁来生成 P。基线内容变化创建新 ID。

一个 `run-id` 表示一次使用同次解析依赖和一致对照约束的验证批次。配置目录记录具体 target/架构、工具链、编译器/SDK、生成器、profile、运行库和选项；`reference-u`、`rust-u`、`reference-p`、`rust-p`、`product-e` 等变体分别存放产物和日志，按当前阶段实际允许的范围创建。对照报告关联双方输入与产物哈希；缺失、跳过或失败分别记录，新批次不覆盖旧结果。

基线清单负责来源与映射，补丁清单负责累计修复身份，运行清单负责该次实际环境、解析依赖、源码快照和结果；根清单仅索引这些记录。清单内路径以参考根为基准使用相对路径，本机绝对路径保存在 `local/` 或相应实际环境记录中，不成为产品配置。通用技术选型和架构理由继续维护在产品 `docs/`，来源/对照审计归入基线 `audits/`。

`build/` 工作目录与同级 deps 缓存均可重建；归档 U/P 基线及发布批次前，将所需输入快照、解析文件、产物和报告保存在基线或运行目录。可复用已经保留并校验哈希的只读归档，但不能仅引用可清理缓存来证明可离线重建；系统 SDK 等外部准备条件另行记录。实际依赖版本只约束该次重建，后续在线构建仍按第 5.6 节解析最新版本。

参考源码、来源清单、补丁、职责映射、许可核验记录和对照记录均不进入产品仓库，也不通过 `.gitignore` 排除这些材料。
参考工作目录通过 `MFS_REFERENCE_ROOT` 或显式路径参数指定，默认可取项目同级目录；不提交开发机绝对路径。
普通产品构建、SDK 消费与安装不依赖参考目录；对照测试显式启用并验证外部参考输入，缺失时报告未验收，不能计为通过。
外部清单的 schema、布局版本及哈希/路径校验逻辑在 P0 随实际清单格式纳入 xtask；不预建空 schema 或 manifest，实际记录继续外置。产品自身的测试夹具、参考程序调用入口和构建脚本可随源码提供；可复用依赖下载与编译缓存写入同级 deps，固定来源与独立参考程序写入基线，需保留的输入/产物/报告按运行批次归档。
产品 `docs/` 按 plans、decisions、design、contracts、guides 分层，README 提供导航及状态；详细规则的权威来源和按需建目录约定见[文档导航](../README.md)。同一规则只保留一处详细定义，计划维护阶段/门禁并引用，选型记录保存理由，AGENTS.md 提供执行摘要。产品 `docs/` 保存自身的公共契约、架构/技术选型决策、构建与使用文档；`docs/decisions/interactive-technology-selection.md` 作为已确认选型记录纳入仓库。本机工具发现、开发机绝对路径、消费者检查明细、来源审计、补丁历史和实际对照/验收材料继续保存在同级参考目录，项目设计文档按需引用其位置。
CI 按阶段从外部目录校验来源哈希、职责映射和对照记录，并检查产品的桥接边界与生成产物。
完整产品源码包含自身生成输入和离线构建所需依赖材料，系统 SDK 的准备方式单独说明；外部参考资料独立准备、独立管理。

## 7. 对象模型、目标与公共接口

### 7.1 核心对象

Runtime、CaptureTarget、CaptureOptions、Session、BackendSample、Frame、Operation/Cancellation 和 MonitorSnapshot 的职责与寿命见[架构设计：核心对象](../design/architecture.md#核心对象)。Runtime 是共享服务入口；会话拥有操作状态，帧存储独立保活；具体 SDK 类型仍在 P3 定案。

### 7.2 C ABI 与包装

以公共 C 头为 ABI 权威输入，采用类型化 opaque handle、固定宽度值、明确结果及可演进结构。布局、失败输出、嵌套扩展、生成声明/常量/导出清单和语言包装边界详见[C ABI 契约设计](../contracts/c-abi.md)。Rust 安全 API 直接复用同一实现，公开动态边界为 C ABI；P3 定案，P5 验证新旧组合和真实消费。

### 7.3 来源快照与布局依赖

来源 key、快照指纹、目标几何与原生资源代次分别表达；仅按实际依赖使资源失效，歧义或无法形成一致布局时拒绝替换来源。详细规则见[来源与生命周期契约](../contracts/lifecycle.md#来源快照与布局依赖)，在 P3 落实。

## 8. 像素、内存与回调契约

### 8.1 公开像素

P3 发布精确描述且独立持有的原格式 CPU Frame，保证目标范围、有效跨度、padding、颜色证据和只读所有权。U/P 仍验收上游统一输出。格式、ROI 隔离及原生有效期规则详见[Frame 契约设计](../contracts/frame.md#公开像素)。

### 8.2 Rust 内存与清理

RAII 管理通常清理，显式 close 报告主要/清理失败；可恢复分配使用内部标准库 fallible 封装，原生地址稳定、注销排空和异常边界分别证明。完整内存、输入与 panic/OOM 保证范围见[Frame 与内存设计](../contracts/frame.md#内存清理与失败边界)。P0 验证所需原型，P3 落实产品寿命，P5 验证绑定。

### 8.3 Custom provider

provider 复制回调表，声明接管点、释放和线程责任；支持与失败路径都校验并恰好释放所拥有资源。详细规则见[C ABI：Custom provider](../contracts/c-abi.md#custom-provider)，具体接口在 P3 定案。

### 8.4 回调重入与执行纪律

P3 明确 provider、日志和释放回调允许的入口、忙状态、日志递归抑制及注销排空。宿主事件循环等待不得形成循环依赖；详见[C ABI 回调契约](../contracts/c-abi.md#回调重入与执行纪律)与[执行模型](../design/execution-model.md)，P5 验证绑定。

### 8.5 可选转换与调用端视图

基础 binding 原始捕获不强制图像框架，薄适配共享格式语义和夹具；只读视图保活 Frame，可写输出隔离，转换保留原样本身份。共享转换仍按实际需求/重复逻辑/端到端性能触发独立决策；详细契约见[Frame：可选转换与调用端视图](../contracts/frame.md#可选转换与调用端视图)。

## 9. 原生线程与窗口协调

P0/P1 保持上游线程、观察和退出行为；P3 落实统一宿主契约、平台执行通道与窗口共享租约。详细规则及后端执行/销毁责任表见[执行模型与窗口协调](../design/execution-model.md)。
每个后端明确创建/访问/销毁者、回调入口、同步等待、注销证据和晚到资源接管；Session 串行调用与宿主线程迁移分开决定。验证锁/等待关系、UI 线程及独立宿主线程、暂停后的独立激活恢复和多 Runtime 租约；不能由 Arc/Mutex 或通用 executor 推断原生线程安全。

## 10. 生命周期与代次

连接、暂停/恢复、资源释放、终结、外部资源移交和独立 Frame 寿命以[生命周期契约设计](../contracts/lifecycle.md)为权威来源。各类代次和状态按拥有者、触发事件、缓存影响和清理责任分别记录，避免单一 connected 标记掩盖资源失效。

### 10.1 失败后的状态与恢复

P3 先定义无更新、设备失效、权限撤销、目标消失、取消/期限及清理失败后的可观察状态与显式恢复；P4 再加入有限自动恢复，保持目标/授权边界。详见[失败后的状态与恢复](../contracts/lifecycle.md#失败后的状态与恢复)。U/P 的原重试和回放语义不提前改变。

## 11. 后端设计与放行条件

本节列出最终产品的后端要求。阶段一完整迁移上游已有方法、窗口 helper/wrapper、管理器截图入口及选源/等待/停用调用链；
按函数/职责清单核验覆盖率，并保留未附加修复的行为。阶段二只改变第 3.4 节规定的窗口校正逻辑。
额外校验、错误唤醒、统一代次/预算、共享租约及严格拒收等增强在阶段三单独实施。
上游截图链中的窗口移动/缩放调用也属于迁移范围，阶段一、二不能提前用严格几何拒收或删除该调用替代，否则无法验证 PR 修复。
阶段三各后端优先发布第 8.1 节定义的原格式 Frame，核心不统一调用 OpenCV；原格式、公开范围和转换能力分别声明，不能将“不做颜色转换”解释为省略来源校验、独立存储或目标隔离。

### 11.1 Windows GDI、PrintWindow 与 ScreenDC

GDI/PrintWindow 明确客户区、DC 归属、位图选择/恢复、top-down 32 位 DIB、行方向和转换规则。
P3 产品路径按第 11.7 节将 GDI、ScreenDC 的 GetBitmapBits 及三者的设备相关位图读取路径迁至显式 CreateDIBSection；PrintWindow 当前使用的 GetDIBits 本身仍有效，替换目的为统一显式布局与独立 CPU 存储。U/P 继续保留各自原调用。
检查原生返回值和失败后资源状态，GetDC/ReleaseDC、CreateCompatibleDC/DeleteDC、位图选择及删除成对管理。
PrintWindow 的前台/后台与伪最小化组合分别验证，不能安全中断的原生调用按返回后检查处理。
ScreenDC 及可见桌面裁剪方法标明遮挡、窗口包含范围和前台操作限制。

P3 另行实现独立的 GDI 全虚拟桌面截图方式；屏幕 DC、单次 BitBlt、DIB 与资源流程见[GDI 全虚拟桌面设计](../design/gdi-virtual-desktop.md)。来源与布局重建以[全虚拟桌面目标](../contracts/lifecycle.md#全虚拟桌面目标)为准，原点、覆盖和像素输出以[全虚拟桌面帧](../contracts/frame.md#全虚拟桌面帧)为准；不将其隐式用于窗口目标或沿用窗口激活/校正 helper。

### 11.2 Windows FramePool

按 SDK 和运行时分别检查 FramePool、边框、光标及附属窗口选项。
以固定参考请求关闭边框/光标、开启附属窗口作为对照，记录请求值、权限结果、实际支持与生效情况。
边框授权等待纳入同一操作预算；选项不可用时按已定义的必需/可选规则处理。

显式管理 D3D 设备、原生帧、staging texture、事件 token 和关闭次序；阶段一保留上游设备及 swap chain 构造行为，产品构造迁移按 ADR 0002 实施并验证窗口副作用。
P3 迁至 CreateFreeThreaded，并在核验用途后以 D3D11CreateDevice 移除未用于捕获的 swap chain 及其目标窗口关联；保留确有原生用途的对象并记录理由，像素、设备能力、线程/回调退出与窗口状态通过对照后采用。具体实现清单见第 11.7 节，事件唤醒优化不随本次接口切换自动启用。
排空残留队列有次数和时间上限，窗口尺寸、ContentSize、texture 尺寸及客户区裁剪在交付前复验。
来源关闭、设备丢失、纹理映射失败使相关状态失效；已有合法样本的无更新回放遵循统一缓存契约。
原生样本身份和 `SystemRelativeTime` 的时钟证据随 BackendSample 传递。

FramePool 与 Desktop Duplication 的 staging 复用按设备代次及原纹理描述判定，至少检查尺寸、格式、子资源布局和采样描述，不能只看尺寸相同。
`CopyResource` 不负责缩放或一般颜色转换；不兼容描述先重建或明确拒绝，转换单独实现，依据 [D3D11 复制约束](https://learn.microsoft.com/en-us/windows/win32/api/d3d11/nf-d3d11-id3d11devicecontext-copyresource)。
映射后验证实际像素格式、行距与取样描述一致，再按声明布局读取；相同宽高换格式/设备也必须覆盖回归。

### 11.3 Windows Desktop Duplication

P3 按第 11.7 节迁移工厂/适配器/device 创建链并采用 DuplicateOutput1；最低接口与格式能力分别探测，DesktopDupWindow 复用同一底层迁移。新格式不自动列为已支持，缺能力或兼容调用的选择条件明确报告。

按目标显示器解析适配器和输出，验证 AttachedToDesktop、桌面坐标、旋转及像素尺寸。
AcquireNextFrame/ReleaseFrame、资源引用、Map/Unmap 成对管理；映射有效期内取得独立像素。
无更新、失去访问、设备丢失、权限失败和来源变化分别分类。
窗口裁剪复验客户区与输出关系，跨输出或未支持旋转明确拒绝；公开 ROI 满足第 8 节的全跨度隔离要求。
冷启动保留经过验证的有效首样本，后续缓存只接受允许的无更新状态。

取帧成功、桌面图像更新和光标更新分别记录。按 [DXGI 帧信息](https://learn.microsoft.com/en-us/windows/win32/api/dxgi1_2/ns-dxgi1_2-dxgi_outdupl_frame_info)处理 `LastPresentTime`、`LastMouseUpdateTime` 与 `AccumulatedFrames`：
仅光标更新时不能把取得资源或完成转换的时间写成新的桌面图像时间；冷启动缺少可比较的图像时间时保留未知，不满足强新鲜度请求。
`ProtectedContentMaskedOut` 等原生内容限制随同次样本传递，由明确策略决定交付或拒绝；不通过像素是否全黑推断保护状态。
这些是 P3 的证据描述及 P4 的策略要求，U/P 的取图与回放行为仍按固定参考迁移。

### 11.4 Linux PipeWire

区分授权 fd/node 与会话 daemon 来源，明确生命周期、停流/恢复和重建条件。
U/P 保留 node ID 选源和原等待；P3 按第 11.7 节采用 PW_KEY_TARGET_OBJECT 及 serial 身份验证，并改用绝对时间等待。数字节点兼容输入只在原授权 remote 内解析，不静默换成任意节点或 daemon；新 provider/SDK 表达在 P3 定案。
采用最新正式版依赖，声明并验证最低运行时能力和全局 init/deinit 所有权，多 Session 与宿主共用依赖时配平引用。
错误回调保存终止原因并唤醒等待，等待谓词包含 ready/failed/disconnected/cancelled。

按实际解析版本核对 fd、properties 及其他输入的消费规则；`pw_context_connect_fd` 在断连或错误时关闭传入 socket，按 [PipeWire Core 契约](https://docs.pipewire.org/group__pw__core.html)配平关闭与失败清理。
授权 socket 的关闭、重复提交、建连失败和重试分别验收；消费后的目标不能静默变成 daemon 来源。

POD 解析覆盖普通 Format、`Choice(None)` 定值、带 Linear modifier 和无 modifier 的协商路径。
检查对象/属性/choice 的长度、类型、对齐、默认元素存在和 builder 容量；shim 验证宏、可变参数提升和数值常量。
尺寸、帧率、格式及缓冲类型的协商范围与实际处理能力一致，并写入能力与构建记录。

首期 CPU 路径支持明确的 packed/single-plane 布局，验证 data/plane 数、modifier、signed stride、chunk/map offset 与有效长度。
其他布局返回不支持。已有映射指针仍须确认访问和同步责任。
共享映射使用适用 Rust 系统绑定或窄 `mmap`/`ioctl` 封装；如采用映射 crate，先核验真实共享映射、原生 fd、偏移和 producer 同步语义，不能用文件 I/O 回退代替协议共享缓冲，也不假定 Rust 标准库提供等价映射接口。
Producer 完成证据与 CPU cache coherency 分开核对；DMA-BUF READ START/END 正确配对，EINTR/EAGAIN 在预算内重试。
同步或清理失败保存错误，归还 buffer 并拒绝发布不确定样本；相关要求依据[Linux 内核 DMA-BUF 文档](https://docs.kernel.org/driver-api/dma-buf.html#cpu-access-to-dma-buffer-objects)。

回调取得的每个 buffer 在成功、拒绝、取消、分配失败和转换失败路径都正确归还。
格式变化推进代次，首个新格式样本前不回放失效帧。无更新回放保留原样本身份和时间。

除内存布局外，检查缓冲/元数据提供的损坏、空样本和有效内容区域等证据；已标记无效的样本不得进入缓存。
原生序列、时间或流连续性变化按证据更新样本/时钟代次；内容裁剪元数据明确选择支持或拒绝，不能静默宣称为完整来源。

### 11.5 Linux Wlr

完整迁移仍覆盖固定上游 Wlr；P3 按第 11.7 节增加 ExtImage 输出捕获，二者是独立协议方法，分别探测服务端能力并验收。ExtImage 不表示全部 Wayland compositor 支持，也不自动扩展窗口目标；固定方法不静默回退到另一协议。

绑定版本取服务端广播与客户端支持的有效交集，逐项检查 output、shm 和 screencopy manager 等必需对象。
维护 global name、输出代理和会话目标的关系，输出移除/重新添加不会改变已选择目标的含义。

v1/v2 与 v3 分别实现事件时序：v3 等待 `buffer_done` 后选择支持的缓冲，发起一次 copy；仅有不支持类型时结束当前请求。
处理 failed、断连、代理创建失败、未知方向标记与取消后的事件。共享内存尺寸满足地址空间、off_t 和协议长度范围。
验证 wl_shm 实际字节序、stride、Y_INVERT 及方向转换。

事件等待按预算处理队列分发及 prepare/read/cancel-read 配对；代理、buffer、pool、映射和连接以明确顺序清理。

P4 的预算覆盖连接后的 registry 同步、缓冲创建、copy 与需要等待的退出步骤，不能只包围等待 ready 的循环。
处理 `wl_display_flush` 的 `EAGAIN`、可写等待和 poll 错误/断连；成功 prepare 后各退出路径完成 read 或 cancel-read，不留下等待其他读者的悬挂状态。
不得在可协作期限路径隐藏无界 roundtrip；如共享宿主连接，使用约定的队列与分发责任，避免意外分发宿主默认队列，依据 [Wayland Client API](https://wayland.freedesktop.org/docs/html/apb.html)。

### 11.6 macOS ScreenCaptureKit

按窗口/显示器创建过滤器，明确客户内容、阴影、光标、颜色配置及 pointPixelScale。
尺寸必须对应可表达的原生像素网格；混合缩放、非整数映射或过滤器几何变化按实际能力处理。
最低 OS/SDK 由所调用 API 与发布矩阵确定。

内容查询和截图完成各自使用稳定、独立保活的状态。超时/取消后到达的结果仅执行清理，不再引用 Session 或发布帧。
限定未完成系统请求数量，超时但仍在途的请求计入额度。
校验像素格式、尺寸、base address、bytes-per-row 和 lock 结果；在 unlock 前完成像素复制或转换。
NSError、权限拒绝、空结果、格式错误和锁失败保留具体诊断。

### 11.7 原生接口现代化

按 [ADR 0002](../decisions/0002-native-interface-modernization.md)将旧兼容接口迁至新路径；[现代化设计](../design/native-interface-modernization.md)维护逐项旧/新入口、原生流程和适用边界。本项已纳入实施，尚未完成接口原型或平台验收，不是仅更新依赖版本的任务。

P3 完成 GDI/ScreenDC/PrintWindow 的显式 DIB、DXGI 工厂与 DuplicateOutput1、FramePool 的 CreateFreeThreaded 及设备初始化、PipeWire 目标选择与绝对时间等待，并接入 ExtImage 输出捕获；新 SDK 不承接上游弃用的 KWin/WlRoots 兼容导出。P4 完成新入口的选法、新鲜度、取消/预算和恢复策略验收，P5 完成真实 ABI/binding、资产与消费者验收。

迁移逐项保留与 P 基线的关系；P0/P1 只记录接口现状和迁移职责，P2 只应用指定 PR。明确旧兼容/弃用的用法在对应产品路径放行前移除；仍有效接口依清单的具体理由迁移，不能把 GetDC、BitBlt、PrintWindow、D3D11 或当前 ScreenCaptureKit sample-buffer 入口仅按年代列为弃用。

每项核验最低 SDK/运行时或 compositor 协议能力、目标范围、格式和颜色、线程/回调、原生资源寿命及错误结果。缺失能力明确失败；确需保留兼容调用时，记录适用环境、选择条件、语义差异及独立验证，不静默降级或换源，不用 U/P/E feature 或重复产品实现维护两套行为。Wlr 可作为独立协议兼容方法存在，固定 ExtImage 缺能力时仍返回不支持。

新入口改变像素、等待、默认方法、最低 OS 或公开格式时，须将差异及依据单列。接口迁移完成不表示性能收益已成立；事件唤醒、共享 producer、转换融合等仍按第 18 节测量。新增格式、HDR、macOS 26 截图入口及额外目标不随迁移自动交付。

## 12. 方法选择、缓存、新鲜度与操作预算

本节为阶段三的产品契约；阶段一、二的方法选择、回放、等待和窗口副作用保持对应参考基线的语义。

### 12.1 选择与单帧流程

固定方法仅使用指定方法；Auto 在目标范围、已编入能力与策略约束内选择候选；None 明确表示不启用内置方法。
只读能力查询返回静态描述与已知环境证据，需要试捕获/授权的探测使用单独入口。
严格后台策略在构造与试用前排除可能激活的方法。
只构造已编入、目标匹配且满足策略的候选；只读查询不启动 producer、线程或权限流程。
固定方法及唯一可用 provider 直接激活，不为无意义测速清理后再二次激活；首样本保留并按统一规则复验交付。
多候选逐个隔离试用，未选 producer 必须停止；上一候选退出/窗口恢复失败时中止后续试用，保留清理责任和主要错误。
消耗一次性授权且不能独立重建的来源，不进行破坏性试用；需要新授权时明确返回，不能假定可重复激活。

一次捕获按以下流程执行：

1. 校验状态，建立 Operation、取消代次、绝对期限和目标/格式快照。
2. 如需选法，逐个试用候选并清理，按确定指标排序，正式激活后重新验证。
3. 在后端规定的线程与资源范围内取得 BackendSample，校验缓冲并转移所有权。
4. 再验证来源、身份、几何和相关代次，应用格式、缓存、时间和预算规则。
5. 将像素与同次取样的元数据发布为独立 Frame，失败路径保存主要/清理错误并归还资源。

连接首帧、常规捕获和缓存复用走同一发布检查。前后来源验证提供非原子的采样证据，能力描述保留该限制。
候选正式激活失败时清理后尝试下一候选；固定方法不隐式改法或换目标。

能力与画面选项按方法、目标和运行时联合表达：客户内容范围、光标、附属窗口、阴影及边框分别记录请求值与生效证据。
P3 定义这些描述，P4 区分必需值和尽力偏好；无法满足必需项的候选在试用前排除，运行时拒绝后也不得降级为成功。
无法证实的生效状态保持未知，Auto 候选及正式激活必须满足同一组必需画面语义。

副作用分别声明可能激活、改变 Z 序、恢复/显示、修改样式/透明度、移动/缩放及触发权限 UI；`NO_ACTIVATE` 仅描述激活行为。
P4 允许宿主分别约束这些动作，并在构造、试捕获、恢复和重新选法前检查；禁止动作所必需的方法返回不支持。
不移动/缩放策略仅在阶段三引入；U/P 继续执行原窗口校正调用，确保 PR 的行为仍可对照。
黑色、单色或透明画面本身不是失败证据；受保护/排除捕获等限制仅在有原生证据时分类，否则报告证据不足，不能据此自动改法或换源。

### 12.2 样本与缓存

交付序号与原始样本身份分开。回放保持 sample ID、原取样时间、source/session/format 代次，标为 REUSED。
NEW 表示取得新样本，UNKNOWN 表示证据不足；像素是否变化与实际取样分别描述。
来源、权限、设备、会话或格式错误使相关缓存失效。
FramePool/PipeWire 等后端的默认等待、回放和连续超时规则在 P0 按固定参考逐项确定，额外缓存策略显式协商。

Fresh-only 要求可靠的请求后取样证据；最大年龄要求可比较的有效取样时间。
时间附时钟域、映射及有效性；转换完成时间和交付时间单独记录。缺少证据时拒绝相应强保证请求。

### 12.3 期限、取消与容量

一个 Operation 使用共享绝对 deadline，覆盖候选试用、正式激活、授权/选项等待和发布检查。
可协作等待按剩余预算退出；不可安全中断的系统调用返回后拒绝晚到结果。操作预算与退出恢复耗时分别报告。
取消信号只作用于关联操作代次，空闲请求不影响下一操作；独立取消句柄可在 Session 关闭后安全查询其终结状态。

P3 确定产品级单帧最大尺寸/字节、排空队列次数/预算、未完成原生请求及待清理状态上限；前两阶段保留参考基线已有的限制。
达到容量返回明确错误，释放本次资源；仍在途的系统回调持续计入额度。

除单帧上限外，P3/P4 明确已交付未释放 Frame、缓存和 pending 的总量核算与可选配额；不同像素格式按实际字节量核算。
库提供的可选适配单独核算转换输出、缓存和临时空间，明确其与核心配额的关系；调用方自行分配的数组/框架存储位于统计边界之外，不宣称核心配额覆盖整个消费进程。
达到配额时明确拒绝或按已协商规则等待，不能覆盖仍被持有的 Frame；同步调用不应无限等待同一调用线程才有机会释放的旧帧。
配额记账状态随存活帧保留，Frame 销毁后归还额度，即使其 Session/Runtime 外层句柄已释放。

## 13. 错误、日志与诊断

结构化错误至少包含类别、操作阶段、后端、原生错误域/码及可读说明。
主要失败与清理失败分别保存，异步失败及时通知等待者；无新样本与捕获失败使用不同结果。

明确错误快照的所有权、有效期和成功后的清除规则；正常状态查询不覆盖先前失败的诊断。
Auto 试用和恢复保留有界的候选失败记录与最终失败原因，不能只留下最后一个清理错误。

日志配置定义发布/替换时机、并发规则、线程和回调重入范围。
日志接收器失败不终止资源清理；桥接与绑定在各自边界处理异常，原生失败诊断不依赖日志成功。
关闭级别的日志在构造消息前过滤；异常清理/析构中的日志失败不传播，限量与过滤不得丢失独立保存的主要错误。
高频事件限量，记录方法选择、拒绝原因、缓存失效、样本/交付身份、延迟和资源统计。
默认诊断不记录像素、窗口标题或输入内容。
运行时查询提供产品版本、ABI、平台与已编入能力；依赖要求随产品说明，完整来源与构建记录保存在外部参考目录。

阶段一的全量后端启用构建和对照报告必须齐全。缺依赖的关闭变体只验证配置能力；缺失平台/场景的结果明确为待验收，不据此宣布完整迁移或越过顺序门禁。

| PR 场景 | 修复后要求 |
| --- | --- |
| 无边框窗口与显示器重合、任务栏占用工作区 | 保持窗口矩形；窗口校正不因任务栏缩小/上移窗口，记录 SetWindowPos 调用和捕获裁剪结果 |
| 每一边相对显示器边界为 ±7/±8/±9px | 验证四边覆盖与容纳的双条件；容差外窗口不能被重合豁免误放行 |
| WS_POPUP 过大、包围显示器或明显越界 | 继续执行原有尺寸钳制/归位路径，并验证后续截图与客户区裁剪 |
| 普通窗口越界或客户区过大 | 按显示器边界校正，保持原调整优先级和调用 flags |
| 最大化/最小化 | 保持对应豁免路径 |
| 任务栏各边、自动隐藏、多显示器负坐标与不同 DPI | 使用实际原生矩形核验，记录原生环境及窗口几何；自动隐藏时实际 rcWork/rcMonitor 关系据实记录 |
| 重复捕获和窗口重新定位后再捕获 | 无边框匹配窗口不被反复调整；真实越界校正完成后截图行为稳定，等待异步窗口消息完成再断言 |

参考程序和 Rust 实现使用相同的自有窗口夹具，记录样式、rcWork/rcMonitor、窗口/客户区矩形、调整调用及结果。
边界判据使用可注入 Win32 调用的确定性测试，窗口状态和实际裁剪再由 Windows 桌面测试验证。

## 15. 构建、绑定与分发

### 15.1 构建与消费

Cargo 编排 Rust 模块、按 target/feature 划分的依赖与测试；`build.rs` 仅集成必要原生编译、探测和生成，`xtask` 组织对照、SDK 打包和跨语言消费，不重复实现 Cargo 已具备的依赖/增量构建能力。
使用 `rlib` 服务 Rust 源码消费者、`cdylib` 提供 C ABI 动态库；静态交付采用 `staticlib` 并单独验收，不向跨语言消费者交付 Rust 动态 ABI。
所有 target、include、宏、ABI 与运行库选项限定到对应编译单元；后端 AUTO 探测与 feature 选择在准备入口完成，显式请求缺依赖后端时失败。
产品发布默认 `release`，保留受检输入路径并配置适用的溢出检查与第 8.2 节的 panic 边界；便携与契约测试至少覆盖 dev/test 和 release，桌面及消费测试覆盖实际发布 profile。
LTO、codegen-units、调试符号/裁剪、目标 CPU 与 panic 策略按实际收益及兼容性分别决策；不默认使用仅本机可运行的 `target-cpu=native` 发布通用包。
CI 使用默认 nightly 执行 rustfmt、Clippy 并实际运行测试产物，记录工具链及实验分配 API 的验证结果；可选诊断工具与其额外组件/配置单独管理，不因诊断工具引入其他默认实验能力，也不维护额外 stable 产品构建矩阵。
最终产品基础构建不构建、下载或链接 OpenCV；图像适配按对应 binding 的独立可选功能/源码提供，依赖不进入基础捕获路径，不新增首版共享转换库。
U/P 目标显式声明验收适配器、所需 OpenCV 和外部参考输入；适配器可独立于 Rust 核心构建，不通过关闭依赖跳过完整基线门禁。
U/P 的 C++ 参考/验收构建及 OpenCV 源码准备遵循第 5.2、5.7 节；首版 Windows 仅实现并核验 VS2026 + MSBuild，同次对照保持原生依赖与运行库一致，本机使用已安装的 VS2026。后续增加 VS2022 或 MSVC-Ninja 时再补对应配置的工具发现、编译、加载和真实桌面验收。

计划命令如下，由准备/迁移阶段建立基础入口，后续步骤随相应阶段实现并写入构建帮助，各入口随所属阶段交付并验收。
运行前按第 5.5–5.6 节解析最新工具链/依赖、落实本机后端配置并设置外部缓存/输出目录；统一入口按需补充本机 feature 参数，以下简写不替代准备步骤。

```text
cargo fmt --all -- --check
cargo clippy --workspace --all-targets -- -D warnings
cargo build --release
cargo test --workspace
cargo test --release --test contracts
cargo run -p xtask -- test-parity
cargo run -p xtask -- test-pr1587
cargo run -p xtask -- test-desktop --enable-desktop-tests
cargo run -p xtask -- sdk --profile release
cargo run -p xtask -- test-image-contracts
```

`test-image-contracts` 校验共享格式/转换契约与夹具；各语言适配在调用端依赖缺失、兼容和不兼容环境分别验证，不将该任务实现为产品共享转换模块。
feature 矩阵按当前平台逐项覆盖，不以无差别 `--all-features` 代替原生依赖和互斥配置验证；无参考资料的基础构建与显式对照任务分别运行。

首版 SDK 包含共享库、所需导入库、公共 C/C++ 头、Rust 源码 crate 及 CMake imported target；原生文件名与第 4 节保持一致，检查导入库/加载器引用，不能只重命名 DLL 留下不匹配的导入信息。
基础 SDK/wheel 不携带 OpenCV 二进制或共享转换组件；对应 binding 可以包含薄适配代码及明确的可选功能声明，安装、导入和原始捕获不自动安装转换框架。
Rust 消费者通过源码 crate 使用安全 API，C/C++ 消费者通过安装或解压 SDK 接入，Zig 等通过 C ABI 接入；纯 C 消费不要求启用 C++ 或安装后端开发头。
如提供 CMake 源码包装，由包装调用统一准备入口与 Cargo，解析最新 nightly 并复用相同配置；静态库单独验证原生依赖传递、链接顺序、运行库和 LGPL 材料。
本地仅构建和测试本机平台；跨系统构建、测试与发布资产验证由第 15.5 节的 GitHub Actions 原生平台矩阵完成。

### 15.2 ABI 加载与语言绑定

导出采用显式 Mfs 符号清单，桥接和依赖实现保持私有。
加载先调用无需版本化结构的最小 ABI/bootstrap 查询，再配置匹配的函数/结构及能力查询。
缺失必需符号、ABI 不符或所请求能力与符号不一致时，报告实际库路径/版本并停止加载。

绑定声明、常量和能力来自同一公共契约，函数签名、可选符号和回调分别通过一致性与运行测试。
基础 Frame 包装如实暴露格式、布局和有效元数据；binding 随包提供 `as_bgr` 等转换及 OpenCV/NumPy/框架薄适配入口，实际可用性由调用方依赖和格式能力决定，名称与签名在对应契约评审中确定。
缺依赖时保留原始帧能力，转换请求返回明确的依赖/能力错误；不将“有转换入口”描述为“无需任何转换实现即可转换”。
无复制借用视图与可写副本分别命名和说明；借用者持有 Frame 所有者，不能将指针转成 Mat/数组后立即释放原生 Frame，也不将任意 stride 的视图冒充紧凑 BGR。
生成常量在绑定中使用具名检查，避免手写数值功能位漂移；仍逐个验证可选符号，不能只验证结构生成结果。
每种绑定定义像素副本、context/函数保活、异常转换、释放线程及关闭行为。
为每种语言规定 64 位 ID、时间、位掩码、指针和 `size_t` 的无损表示，以及无法表示时的拒绝规则。
JavaScript 对超出安全整数范围的值使用 bigint 等无损表示；Java 的无符号映射、各语言数组/Buffer 长度上限和整数窄化分别检查。
长度校验在构造原生视图、读取指针或分配宿主缓冲之前执行；生成类型不替代这些运行时规则。
显式 close/dispose 负责可观察的释放；GC/finalizer 兜底遵守后端线程约束，不在任意回收线程执行未经调度的窗口恢复或原生终结。
首批 Rust 所有者类型/显式 close、C++ RAII 与 Python context manager/显式 close 提供确定性清理，已释放资源不重复释放，关闭后调用明确拒绝；失败恢复责任按第 10 节保留并可观察。
Python wheel 按平台/架构分发，明确系统 ABI、最低 OS 及外部运行依赖；最终 wheel 在干净环境安装并执行契约测试。
Python binding 采用分阶段路线：首版验证使用 ctypes 调用公共 C ABI，声明、常量和能力与公共 C 头保持同源并核对布局、签名及加载协商；在 `nightreign-overlay-helper` 中验证捕获线程、Frame 保活、Qt/NumPy 交接和冻结分发。首版 Python 源码包及适用 wheel 作为 GitHub Release SDK/配套资产提供，首版不上传 PyPI。
后续版本迁移为 PyO3 + maturin，继续通过公共 C ABI 接入同一捕获核心。沿用已验收的像素、所有权、错误和线程契约，使用相同夹具对照 ctypes 与 PyO3 路径；核验 Python 对象/缓冲协议、解释器/ABI 与 wheel 兼容、跨线程释放及 PyInstaller 集成后切换主交付路线。保留 `maafw_screencap` 导入名，公共接口变化按 SemVer 声明；具体接口和迁移适配在 P2 验收后设计。
NumPy、OpenCV 等集成复用调用方显式准备的依赖，分别覆盖缺失、兼容和不兼容状态；核验实际版本、加载身份和行为，不假定各生态封装自动共用同一份 OpenCV。
Python 不将特定 `opencv-python` 分发变体硬编码为基础必装项，不自动覆盖调用方已有 headless/contrib 等 `cv2` 环境；其他语言同样通过其公开绑定/构建入口接入，避免依赖包内部私有二进制布局。

### 15.3 产品资产与外部工程记录

正式产品资产包含原生 SDK、完整产品源码、Python 分发物、必要依赖/许可材料和 SHA256SUMS。
首版资产列明基础核心、各语言绑定及薄适配代码；验证未附带 OpenCV 二进制、共享转换库或意外的 OpenCV 链接/加载依赖。

产品版本、ABI、目标平台、最低运行要求与依赖信息随对应资产提供；开发构建和干净发布提交分别标记。
来源清单、固定上游/PR 身份和许可核验写入同级参考目录的基线/补丁清单与 `audits/`；每次构建、U/P/E 对照及发布消费的工具链、解析依赖、源码身份、原生哈希关联和 provenance 按 `runs/<run-id>/` 归档，根清单仅提供索引。本机工具发现与消费者路径单独存入 `local/`。
上述工程记录、参考程序和补丁不进入产品仓库、源码包或 SDK；需要交付对照证据时从外部目录单独提供，并适用各自许可。
完整产品源码在预先准备好该次构建解析的依赖与系统 SDK 后可离线重建；快照只服务该次重建，后续在线构建仍解析最新版本，不读取参考目录中的源码、头文件或库。

逐平台核对 DLL 传递依赖、ELF NEEDED/RUNPATH、Mach-O install name/rpath 和部署目标。
随包依赖从包内相对位置解析，系统依赖列出最低要求；SDK/wheel 移动目录、移走构建树并清除开发搜索路径后重新消费。
源码重建和最终消费以交付资产为输入。常规 CI 默认关闭真实桌面测试，原生桌面任务单独运行并报告跳过原因。
常规 PR/分支 CI 也生成并验证所声明平台/架构/包类型的完整资产集合，不把打包与消费验证只留到发布标签。
在外部发布记录中核对构建结果、SDK 与 wheel 实际包含的原生库身份/哈希一致；版本、ABI、包名和项目链接同步校验，不把能加载另一份开发库记为最终资产通过。

上述分工从 P0 原型开始适用，按阶段逐步加入必需任务；PR/分支验证与标签发布均复用同一平台矩阵和资产检查，Action 与工具依赖遵循第 5.6 节。

### 15.6 提交、标签与发布触发

**首次发版前必须先主动提醒用户在 GitHub 仓库配置发布所需的相关密钥，覆盖 SDK、Rust crate 及各语言 binding（包括 wheel 和其他生态包），预发布同样适用。** 提醒时依据实际发布渠道与 Workflow 列明所需密钥名称、用途和配置位置；各 binding 后续独立首次发布、既有产物首次启用新的发布渠道时，也须检查对应配置并提前提醒。首版按 GitHub Release 实际需要准备，后续启用 crates.io、PyPI 等渠道前再次落实其发布配置。

该提醒应在创建或推送首次发布标签、手动触发发布 Workflow、首次向包仓库上传之前完成。发布准备时核对所需配置是否齐全，缺失项明确告知用户补齐；密钥值由用户在 GitHub 仓库侧配置，文档与日志只记录名称和配置状态。

提交规范见第 18 节，项目版本与标签遵循第 4 节。发布准备中的代码、版本及文档修改先形成提交，单独推送目标分支并等待该提交的必需 CI 验收通过，再按发布授权创建标签，在另一次推送中仅推送该标签。
同一次推送不得同时包含分支修改和 tag；发布入口不得使用 `--follow-tags` 或以 `--tags`、`--all`、`--mirror` 批量推送引用。显式关闭自动跟随标签，避免本地 `push.followTags` 配置将标签混入分支推送。

以下仅为发布流程的命令示意，分支提交验收通过与标签创建分别发生在两步之间：

```text
git push --no-follow-tags origin HEAD:refs/heads/<branch>
git push --no-follow-tags origin refs/tags/v<version>:refs/tags/v<version>
```

按 [GitHub Actions 触发与过滤规则](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax)，分别定义 PR/分支验证入口和仅匹配版本 tag 的发布入口；公共任务可通过可复用 Workflow 调用，避免同一引用变更命中重复发布路径。
分支验证后再触发标签发布是两个明确阶段；标签任务不自动提交并推送分支修改，以免形成触发循环或额外记录。
标签必须指向已通过分支验收的提交；由于依赖跟进最新版本，标签任务仍须验证该次实际解析依赖及最终资产，不能直接用历史依赖集合的通过结果替代。

### 15.7 分阶段公开分发目标

分发分为两步：**首版仅通过 GitHub Release 提供 SDK/配套源码与 binding 资产，Rust crate 不上传 crates.io，Python binding 不上传 PyPI；后续版本再启用公开多渠道。** GitHub Release SDK 包含 Rust 源码 crate 与首版 ctypes Python binding，适用 wheel/安装包可作为同次 Release 资产供安装和消费验收。
后续版本中，已交付语言 binding 进入其官方或权威依赖分发渠道；Rust/C/C++/Python 按首批范围交付，Python 实际消费者优先验证，其他语言随相应 binding 实现和消费验收后启用渠道。Python 后续采用 PyO3 + maturin 的迁移与各包仓库启用分别验证，具体版本安排在发布准备时确定。

| 交付项 | 首版交付 | 后续公开渠道与要求 |
| --- | --- | --- |
| 原生 SDK、C/C++ 头与 CMake package | GitHub Release 安装/解压资产、源码与校验信息 | 继续提供 GitHub Release SDK |
| Rust crate | GitHub Release SDK/源码包中的 crate，供源码依赖使用 | 启用 crates.io 发布，明确 nightly 与原生构建要求 |
| Python binding | GitHub Release SDK 内的 ctypes binding 及适用 wheel/源码包 | 迁移至 PyO3 + maturin，并在后续版本启用 PyPI；复用宿主兼容 cv2，基础安装不强制下载 OpenCV |
| C# binding | 按后续 binding 阶段交付 | 启用 nuget.org，按原生平台资产和 .NET 消费方式验收 |
| Java binding | 按后续 binding 阶段交付 | 启用 Maven Central，供 Maven/Gradle 依赖使用；构建/上传工具在该 binding 阶段选择 |
| Go binding | 按后续 binding 阶段交付 | 发布模块版本 tag，通过 Go modules/proxy 获取并由 pkg.go.dev 收录；交付前明确模块路径、子目录 tag 与项目版本映射 |
| Node.js binding | 按后续 binding 阶段交付 | 启用 npm 公共 registry（registry.npmjs.org），核验原生资产安装与加载 |

各渠道在启用前确认包名/namespace、维护者身份、版本映射和相应原生资产组成，按第 4 节保持项目版本与包元数据一致。GitHub Release 与后续各包仓库的发布结果分别记录；首个版本、新增 binding 首次发布及既有产物首次启用新渠道均执行第 15.6 节的提前提醒和凭据配置核对。

渠道依据：[Cargo 发布](https://doc.rust-lang.org/cargo/reference/publishing.html)、[Python 分发](https://packaging.python.org/en/latest/overview/)、[NuGet 发布](https://learn.microsoft.com/en-us/nuget/nuget-org/publish-a-package)、[Maven Central/Gradle 发布说明](https://central.sonatype.org/publish/publish-portal-gradle/)、[Go 模块发布](https://go.dev/doc/modules/publishing)、[pkg.go.dev 收录机制](https://pkg.go.dev/about#adding-a-package)、[npm 公共 registry](https://docs.npmjs.com/packages-and-modules/contributing-packages-to-the-registry/)。

| SDK 公共 ABI 与安全 API | 尚未最终定案 | P2 验收后在 P3 确定具体公共类型/结构前缀、所有权与释放、错误/版本协商、声明生成和回调契约；当前计划作为设计起点 |
| GDI 全虚拟桌面扩展 | 已纳入规划，尚未实现或验收 | 按 ADR 0001 在 P3 实现独立目标/方法及原始输出，具体 SDK/ABI 值届时定案；P4/P5 分别验证策略和消费，不进入 U/P |

已明确 Python 悬浮窗消费者、ctypes 首版验证 → PyO3 + maturin 后续迁移，以及 GitHub Release 首版 → 后续公开多渠道的安排。后续具体图像视图/所有权、声明、依赖 feature 和打包参数按原型证据及阶段契约细化；仅在发现现有路线无法满足验收，或出现影响范围、兼容性与发布方式的新取舍时重新讨论相应选型。

## 18. 性能、维护与上游更新

性能优化先建立同约束基准，记录连接、首帧、持续 p50/p95/p99、新样本帧率、样本年龄、CPU、唤醒、线程、句柄/fd、内存和图形资源。
基准固定来源、像素格式、分辨率、更新频率、策略、OS、驱动与工具链，同时记录正确性结果。

P3/P5 在启用原格式与适配路径时即验证到消费者可用图像的完整成本，分别测量原生等待、GPU 读回、核心复制、格式转换、binding 包装及必要连续化/框架复制；不只统计捕获 API 返回时间。
消费者可直接使用原格式时验证省去转换的收益；必须使用 BGR 等格式时，比较“原生映射直接转换为独立输出”与“先复制原格式再由调用端转换”，记录每帧复制字节量、分配、额外存储及延迟。
固定最终格式、目标范围、颜色和所有权约束后比较结果，不把将工作移到 binding 当作消除工作，也不以无界延长映射/producer 保留期冒充零复制。
调用端适配启用的优化能力在交付前验证；P6 按第 8.5 节的实际触发条件评估共享模块或原生融合及其他新增优化，不因列入候选就预先实现，基础核心持续保持无 OpenCV 依赖。

区分冷启动、预热后持续采样和无更新回放；一次冷样本耗时仅能作为该次启动代价，不能当作持续捕获性能。
P6 如调整 Auto 排序，固定预热/样本数、失败率、稳定平局规则及清理成本；先满足同一画面/副作用约束，再比较性能。
选择测试使用可注入计时与已知候选结果，基准使用真实时间；不让桌面瞬时抖动成为确定性回归断言。

以下仅列为 P6 条件评估项，正确性成立不等于收益已经成立；没有稳定收益时保留通过验收的实现。

| 评估方向 | 前置证据与不可削弱的边界 |
| --- | --- |
| 减少像素复制/缓冲复用 | 先按路径统计每帧完整复制次数、字节量、分配和耗时；区分拥有像素与借用视图，评估所有权转移或不可变共享；保留 Unmap/Unlock、归还 producer 或 provider 缓冲前的必要复制/保活 |
| 转换位置与融合 | 首版比较原格式直用与 binding 复用宿主转换；共享原生模块/融合按触发条件另行立项。同最终输出下核验总复制、分配、依赖体积、端到端延迟及优化覆盖，不使基础绑定强制依赖 OpenCV |
| 减少来源查询 | 先统计每帧身份、拓扑、几何查询次数与耗时，再考虑单次操作内复用中间结果；保留独立前后验证、目标寿命及布局拒收，不能以固定 TTL 全局快照替代 |
| FramePool 事件唤醒 | 比较静态/动态、多 Session 的 CPU、唤醒、线程/句柄与更新延迟；事件回调只通知，WinRT 对象仍由所属 MTA 通道操作；通知 context 独立保活并合并到帧、任务和 stop 唤醒，验证不丢单次更新及退出竞争 |
| 原生等待、调度与批处理 | 基于 Rust/平台绑定评估事件合并、原生队列及适用批处理；引入执行器或 io_uring/GCD 等机制前核验线程约束和实际收益，比较同契约下端到端延迟、样本年龄与资源成本，不假定通用 I/O 改进必然加速 GPU 取图 |

共享观察调度、producer 共享及异步池各自验证语义，再测量收益和资源成本；不因减少线程或复制次数就默认启用。
异步流定义有界背压、丢帧、取消及关闭契约；内容变化接口只报告有证据的更新信息。

所有提交遵循[约定式提交 1.0.0](https://www.conventionalcommits.org/zh-hans/v1.0.0/)，采用 `<type>[可选 scope][可选 !]: <description>`，正文与页脚按规范填写。
`feat` 表达新功能，`fix` 表达修复，其他类型按目的采用 `docs`、`build`、`ci`、`refactor`、`perf`、`test`、`chore` 等；破坏性变更使用 `!` 或 `BREAKING CHANGE:` 明确声明，不能仅从类型推断兼容性。
本地提交检查与 Actions CI 共同校验提交消息；采用 squash 合并时，待生成的最终提交消息也须通过同一规则。版本升级结合公共 API 兼容性按第 4 节判断，不仅根据提交类型机械决定。
来源适配、行为设计、安全修复、格式整理和性能修改分别说明目的及验证。
Rust 采用 rustfmt 与适用 Clippy 检查，原生桥接及手写绑定分别采用固定格式规则；纯格式变更与逻辑变更分开，生成文件由生成器维护。
注释准确描述借用、共享、深拷贝、代次和释放责任；独立状态属性不为减少行数强行压成单一状态，不为少量分支引入通用框架。
公开契约与生成声明同源，状态机、锁关系及资源释放规则随实现维护。
上游更新使用单独提案，在同级参考目录记录基线和依赖变化、原生差异、需调整的设计决策，并重跑受影响验收后更新该目录内的 manifest。
若将来选取已包含 PR #1587 的上游基线，核对实际提交与等价改动后消除重复补丁，更新 U/P 的来源关系和回归证据。
版本、标签和发布流程由项目的发布规则与实际授权控制，按第 15.6 节分开推送分支与标签。
